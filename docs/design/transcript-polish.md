# 설계: 스마트 교정 (대화 내용 교정 제안, 코드 이름 polish)

> 상태: 0.4.3 출시(v1, ARCHITECTURE v3.65). v2 개발 중(2026-10-23, 브랜치 `feat/polish-v2`, ARCHITECTURE v3.68, 아래 "v2"). 코어 `src/tractus/polish.py`·`tractus polish`, 앱 `PolishControls.tsx`·`polish.ts`, 측정 `bench/polish_eval.py`.

## 한 줄 요약

변환이 끝난 노트에서 AI가 대화 내용 전체 흐름을 보고, 잘못 들은 말이 있는 문장(타임스탬프 단위)만 고친 문장을 **제안**한다. 사용자가 문장마다 받거나 버린다.

## 왜 하나

- 남은 오류의 대부분은 모델이 잘못 들은 말이다. 자르기 손실은 0.15%p뿐이고(docs/design/korean-itn.md), 숫자 표기는 ITN이 맡는다. 실제 노트에서는 분야 용어("온톨로지", "인시던트", "파드")와 사람 이름이 자주 틀린다.
- 대화 전체 맥락과 정답 후보(자주 쓰는 단어·참석자·제목·메모)를 보면 고칠 수 있는 오류다.

## v2: 교정 + 정리 (소유자, 2026-10-23)

v1은 "잘못 들은 말만" 고쳐 실제 노트에서 줄의 약 20%에 낱말 한두 개가 바뀌는 데 그쳤다. 사용자에게는 AI를 쓴 티가 거의 나지 않았다(소유자: "너무 소극적으로 개입"). 프롬프트가 군말·띄어쓰기를 금지했고, 거르기(`same`·`short`·`edge`)가 그런 제안을 버렸다.

- **역할을 녹취록 교정으로 넓혔다**(`prompts/polish.md`): 잘못 들은 말 + 군말·바로 이어진 반복 + 문장부호·띄어쓰기 + 맞춤법. 말투(구어체 어미·존댓말)와 뜻은 그대로, 문장 경계는 옮기지 않는다. 확실하지 않은 낱말은 두고 나머지만 고친다.
- **문맥을 녹취록 전체로**: 고칠 범위는 5천 자 그대로, 문맥은 범위 앞뒤 30문장 → 녹취록 전체(`FULL_CONTEXT_CHARS` 6만 자 이하일 때, 넘으면 앞뒤 30문장). v1 측정에서 일관성을 바꾼 것은 고칠 범위의 크기였지 문맥이 아니다.
- **`kind`에 `style`**(군말·문장부호·띄어쓰기·맞춤법만 고침)을 더했다.
- **거르기:** `same`은 원문과 완전히 같을 때만, `short`는 50% 미만(군말을 지우면 줄어든다), `edge`는 앞·뒤에 낱말을 더했거나 군말(`FILLERS`)·되풀이가 아닌 낱말을 셋 이상 뺐을 때만, `rewrite` 표시는 띄어쓰기·문장부호만 달라진 자리를 세지 않는다.
- **받은 용어·이름 교정을 모아 자주 쓰는 단어로 제안**(앱 `polish.termsFromSuggestions`): 받은 제안 중 `term`·`name`의 바꾼 자리마다 `vocab.termFromEdit`, 알림 하나로 묻는다(v1은 하나만 받았을 때만).
- 하지 않은 것(소유자): 교정·정리를 나눠 보이기, 끝난 뒤 고친 수 요약, 새 측정. `bench/polish_eval.py`의 CER은 정리가 대본 대비 원래 나쁘게 나오므로 v2 판정에 쓰지 않는다.

## 결정 (소유자, 2026-10-22)

1. **문장(세그먼트) 단위로 제안하고 사람이 받는다.** 화면은 타임스탬프마다 제안을 보이고 받기·버리기 단추를 준다(구체 모양은 함께 정한다).
2. **고친 양에 상한을 두지 않는다.** 대신 규칙 위반은 걸러 낸다(아래).
3. **정답 후보를 함께 준다.** 회의록과 같은 블록(`minutes.build_input`: 대화 내용 + 사용자가 적은 메모 + 확인한 참석자 이름 + 자주 쓰는 단어 50개).
4. **받은 용어 교정은 자주 쓰는 단어로 이어 준다**(앱의 `vocab.termFromEdit`, 화면 단계).
5. **사용자가 직접 고친 문장은 고치지 않는다**(문맥으로만 보낸다).

## 구조 (`polish.py`)

- **고칠 범위 5천 자씩 + 앞뒤 30문장 문맥, 4개 동시.** 한 번에 대화 전체(1–2만 자)를 맡기면 고칠 곳의 일부만 돌려줘 실행마다 크게 달랐다(아래 측정). 범위가 작으면 끝까지 훑는다. 앞뒤 30문장(약 5–10분)과 제목·메모·자주 쓰는 단어가 문맥이다.
- **AI 출력:** `{edits: [{id, text(고친 문장 전체), kind: term|name|number|word}]}`. 범위 밖 ID·같은 ID 두 번·빈 문장은 재요청(`check`).
- **코어가 버리는 것:** 문장부호·띄어쓰기만 다른 것(`same`), 원문 글자의 75% 미만으로 짧아진 것(`short`: 내용 빼기), 문장 앞·뒤에 낱말 셋 이상을 더하거나 뺀 것(`edge`: 앞뒤 문장의 말을 끌어오거나 넘기기, `moves_edge`). 프롬프트에도 같은 규칙이 있다.
- **코어가 표시하는 것(버리지 않는다):** `number`(원문에 없던 숫자가 생김: 짐작한 숫자), `rewrite`(한 자리에서 낱말 셋 이상을 바꿈: 짐작해 다시 쓴 것일 수 있다). 화면은 이 둘을 눈에 띄게 보여야 한다.
- **저장:** `<노트>/polish.json`(`suggestions: [{id, start, before, text, kind, flags}]`). transcript.json은 바꾸지 않는다. 받기는 기존 `apply_text_edits`(원문 보존, 단어 싱크 옮기기)로 하고, 누가 고쳤는지 표시할 키는 화면과 함께 정한다.

## 측정 (2026-10-22, AI: gemini-3.8-flash-high, 앱 기본 경로)

### 가상 회의 (정답 있음)

`tests/fixtures/eval/meetings` 5개(각 약 3분)의 대본을 `say`(Yuna·Grandpa 번갈아)로 읽혀 제품과 같은 `tractus transcribe`(1.7B)로 변환하고 대본과 비교했다. `say`가 영어 약어를 철자로 읽어 변환 CER이 실제보다 높다(21.45).

| | 값 |
| --- | --- |
| CER 전 → 후 | 21.45 → **18.96** |
| 제안 / 나아짐 / 같음 / 나빠짐 | 20 / 16 / 2 / 2 |

- 고친 예: "애비용" → "AWS 비용", "우서버" → "GPU 서버", "돈리합니다" → "동의합니다", "BPO 품에 보류함 여겨" → "GPU 구매 보류와 엮여", "일레스틱 사크" → "엘라스틱서치".
- 나빠짐으로 잡힌 것은 대본은 영문("Redis", "latency"), 변환·제안은 한글이라 채점이 흔들린 경우가 대부분이다. 숫자를 짐작한 사례 하나("옵이천" → "5억 2천", 정답 5억 1천)는 `number` 표시가 잡았다.
- 처음 시험에서 첫 문장을 통째로 뺀 제안이 있어 `short`·`edge` 거르기를 넣었다.

### 실제 노트 (소유자 요청, 정답 없음, 노트 폴더에는 쓰지 않음)

소유자 Mac의 녹음 노트 5개(30–63분, 문장 1,283개). 검토표는 로컬에만 둔다.

| 설정 | 노트당 제안 | 두 번 실행의 겹침(자카드) | 노트당 시간 |
| --- | --- | --- | --- |
| 한 번에(1–2만 자), 온도 0.2 | 1–47 | 0.12–0.45 | 약 1분 |
| 한 번에, 온도 0 | 1–38 | 0.10–0.45 | 약 1분 |
| **5천 자씩 + 앞뒤 30문장** | **40–80** (두 번 돌려도 ±6) | **0.57–0.68** | 1–2분 (4개 동시) |

- 온도는 일관성을 바꾸지 못했다. 범위 크기가 바꿨다.
- 5천 자 설정의 제안 277개: `rewrite` 12개(4%), `number` 11개.
- 눈으로 본 판정(10-06 노트 73개): 대부분 맞는 교정이다(로고 → 로그, 인계치 → 임계치, 인시덤·이순도 → 인시던트, 언론·알로선 → 얼럿, 쳤다음 → 셧다운, 이어스 파스 → IaaS PaaS). 약 10–15%는 짐작이다(“완만한 수로 마치는 얘기요” → “방안으로 맞추는 게 맞고요”, 일본어로 잘못 받은 줄 → 한국어 문장). 대개 `rewrite` 표시가 붙는다.

## 화면 (소유자, 2026-10-22)

- **이름:** 화면은 `스마트 교정`(영어 Smart fix, 2026-10-22 소유자가 `AI 다듬기`에서 바꿈: `스마트 검색`과 짝). 코드·CLI·파일은 `polish` 그대로.
- **시작:** 변환이 끝난 녹음 노트의 대화 내용 툴바 `스마트 교정`(양옆 패널이 아니다). AI 서비스는 요약 탭에서 고른 것을 쓴다.
- **도는 동안:** 대화 내용 영역 가장자리에 빛 한 줄기가 돌고 안쪽이 숨 쉬듯 밝아진다(`.polish-frame`, 같은 격자 칸에 겹쳐 스크롤하지 않는다, 폭 1180px 미만에서는 숨김). AI가 아직 보지 않은 줄은 위에서부터 물결처럼 빛난다(`.seg.is-glow`). 움직임 줄이기에서는 멈춘 빛. 구간(5천 자)이 끝날 때마다 그 구간의 빛이 꺼지고 제안이 나타난다(progress 이벤트의 `suggestions`·`range`). 단추에 `스마트 교정 중… {done}/{total}`.
- **제안:** 그 줄 바로 아래에 낱말 diff(지운 말 줄 긋기 → 새 말 파랑 바탕)와 `숫자 확인`·`다시 쓴 문장` 표시, `수락`·`거절`.
- **많을 때:** 대화 내용 위에 붙는 막대 `교정 제안 {n}개 · 확인할 것 {m}개` + `모두 수락`(표시 없는 제안만) · `모두 거절`.
- **받은 줄:** `수정됨` 자리에 `스마트 교정됨`(파랑, 사람이 고친 `수정됨`은 memo 색). 원문은 남고 ⌘Z로 되돌린다. 하나만 받았으면 자주 쓰는 단어를 제안한다(`vocab.termFromEdit`).
- **남은 제안:** polish.json에 남아 노트를 다시 열어도 보인다. 제안을 만든 뒤 그 줄을 누가 고쳤으면 보이지 않는다(`before`가 지금 문장과 다름). 다시 누르면 새 제안으로 바뀐다.

## 코어·앱 계약

- `tractus polish <노트> run [--provider P] [--model M] --progress-json`: `stage polish` → 구간마다 `progress {done, total, suggestions, range: [첫 ID, 끝 ID]}` → `done {suggestions: N}`. AI를 기다리는 동안 고친 줄의 제안은 저장하지 않는다(`note_lock` 안에서 다시 읽어 거른다).
- `show` → `{suggestions}`(지금도 맞는 것만), `accept`·`reject` stdin `{"ids"}` → `{changed, remaining}`·`{remaining}`. 받기는 `apply_text_edits`에 `by: "ai"`(선택 키 `corrected_by: "ai"`, 사람이 다시 고치거나 원문으로 되돌리면 지운다).
- Rust: `polish_start(id, job, provider)`(요약과 같은 `llm_cmd`·`busy`, 이벤트 `job` + `kind: "polish"`), `polish_resolve(id, ids, accept)` → 고친 회의. `load_meeting`이 `polish.json`의 제안을 `polish`로 싣고 `Segment.corrected_by`를 넘긴다.

## 남은 것

- 프롬프트를 바꾸면 `bench/polish_eval.py synth`(가상 회의)로 나아짐·나빠짐을 본다. 실제 AI 스모크(`pytest -m llm`)는 아직 없다.
- 실행 취소(도는 중 멈추기)는 없다(요약·회의록과 같다).

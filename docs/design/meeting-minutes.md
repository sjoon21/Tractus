# 설계: 회의록 (요약에서 꺼낸 별도 문서)

> 상태: 코어 시안 (2026-10-20, `src/tractus/minutes.py`). 앱 화면은 아직. 결정은 끝의 "결정" 절, 남은 질문은 "열린 질문" 절.

## 한 줄 요약

녹음 노트의 오른쪽 패널에 `회의록` 탭을 따로 둔다. AI는 근거가 달린 구조 데이터만 내고, 표·제목·참석·형식은 코어가 그린다. 만든 뒤에는 앱 안에서 고쳐 그대로 사내 위키에 붙인다.

## 왜 하나

- **회의록을 쓰는 사람이 많은데, 지금은 `회의록`이 요약 유형 6개 중 하나다.** 출력은 옛 요약 형식(결정 사항·할 일·주제 목록)이고, 실제 팀 회의록의 모양(요약 표, 안건별 논의, 팀별 할 일)을 만들 수 없다. 사용자 피드백: "요약 탭 구조가 그렇게 유용하지 못하다".
- **회의록은 고쳐서 올리는 문서다.** 요약은 읽기 전용이라 결국 복사해 위키에서 다시 쓴다.
- **앱이 이미 아는 것(날짜, 참석자 이름)을 AI에게 맡기면 지어낼 여지만 생긴다.**

## 실제 회의록에서 본 형식 (사내 회의록 2건, 2026-10)

내용은 옮기지 않고 모양만 적는다. 두 건도 서로 형식이 다르다.

| | 목록형 | 표형 |
| --- | --- | --- |
| 머리 | `**주요 안건:**` 한 줄 | `참석: A팀, B팀, C팀` |
| 요약 표 | 없음 | `구분 / 논의 내용 / 조율 사항` (안건마다 한 줄) |
| 본문 | `### 1) 안건` 아래 굵은 이름표 목록(`기존 기획안`, `기술적 이슈`, `아이디어`, `대안 및 범위 조정안` 등), 한 단계 아래 세부 | `### 안건` 아래 굵은 이름표 목록 + `**접근 방식 정리**:` 한 단락 |
| 미결 | 안건 제목 앞 `[추가 논의 필요]` | 없음 |
| 할 일 | 표 `작업 내용 (담당 팀) / 비고` | 표 `팀 / Action Item` (팀별로 묶음) |

공통점:

- **없는 칸이 없다.** 일시 표, 목적, 기한, 도식, `한계` 절은 두 건 모두 없다. 기한도 없다.
- **팀이 주어다**("B팀 제안", "A팀 검토"). 회의록에서 가장 중요한 정보이면서 가장 지어내기 쉬운 정보다.
- **범위 결정이 중요하다**: "이번 버전 범위에서 제외", "차기 버전에서 재확인"처럼 하지 않기로 한 것과 그 이유를 적는다.
- 이름표는 정해진 목록이 아니라 회의마다 다르다.

다른 LLM이 만든 범용 회의록 프롬프트(사용자가 2026-10-20 공유)는 일시 표·목적 3개·도식·`한계` 절을 늘 만들게 한다. 실제 회의록에 없는 칸을 채우게 하므로 **이 설계는 그 칸을 만들지 않는다.** 결론 먼저, 범위 안·밖 구분, 제안 → 한계 → 결정의 인과, 이견 양쪽 서술, 미결 분리, 추임새 제거는 가져온다.

## 사용자 경험

1. 녹음 노트의 오른쪽 패널이 `요약 · 회의록 · AI 질문 · 메모`가 된다. 메모 노트(녹음 없음)는 지금처럼 `요약 · AI 질문`이다.
2. `회의록` 탭에 `회의록 만들기` 단추가 있다. 변환 전 노트·AI 키 없음은 요약 단추와 같은 방식으로 막는다.
3. 만든 뒤에는 회의록이 보인다. 형식은 하나이고, 내용이 있는 부분만 그린다(아래 "그리는 형식").
4. 항목마다 근거 시각 칩이 붙고, 누르면 그 자리부터 재생한다(요약과 같음). 근거와 다른 숫자가 든 줄에는 `숫자 확인` 표시가 붙는다.
5. **고치기는 칸 단위다.** 줄을 두 번 누르면 그 줄을 고치고(Enter 저장, Esc 취소), 비우면 지운다. 할 일은 내용·담당·기한 칸을 따로 고친다. 근거 ID는 그대로 남는다(Markdown 통째 편집은 근거를 끊어서 하지 않는다, 2026-10-20: 경쟁 제품 HeyMoa도 칸 단위).
6. 할 일의 `담당 미정`·`기한 미정`은 눈에 띄게 보인다. 담당·기한이 없는 할 일은 실행되지 않기 쉽다(브런치 「좋은 회의록이란」, 2026-10-20).
7. 단추는 둘이다. `복사`는 위키용 회의록 전체(Markdown), `짧게 복사`는 회의 직후 메신저로 보내는 짧은 판이다. 둘 다 같은 데이터를 코어가 그리고(AI 호출 없음), 근거 시각은 넣지 않는다.
8. 대화 내용·참석자 이름을 고치면 요약처럼 낡음 안내와 `다시 만들기`가 보인다. 회의록을 고친 적이 있으면 `다시 만들면 직접 고친 내용이 사라집니다.`를 먼저 묻는다.
9. 예전에 만든 `회의록` 요약(`summary.json`)은 회의록 탭에 `이전 형식`으로 보인다(읽기만). `회의록 만들기`를 누르면 새 형식으로 만든다. 옛 파일은 지우지 않는다. 요약 탭의 유형 메뉴와 만든 요약 목록에서는 `회의록`이 빠진다.

**짧은 판 (짧게 복사)**

```text
[회의록] 결제 기능 2.0 회의 (10.20)
짧게 정리했습니다. 틀린 부분은 알려 주세요.

정한 것
- 해외 카드는 2.0에서 빼고 2.1에서 다시 봄
할 일
- 원화 결제 범위 문서 정리 — 김지훈, 다음 주 수요일
- 배치 분할 검토 — 담당 미정, 기한 미정
아직 안 정한 것
- 환불 정책
다음에 볼 날: 다음 주 화요일
```

## 데이터

새 파일 종류를 만들지 않고 **요약 v2의 key `minutes`** (`summaries/minutes.json`, `kind: "minutes"`)에 저장한다. 노트 완성(`enhanced`)과 같은 방식이라 목록·삭제·낡음·녹음 추가 시 근거 ID 옮기기가 그대로 동작한다.

```jsonc
{
  "schema_version": 2,
  "template": "minutes", "template_name": "회의록", "kind": "minutes",
  "title": "...", "overview": "",
  "minutes": {                                   // AI 원본 (근거 포함)
    "agenda": "한 줄: 이번에 다룬 안건",
    "topics": [{
      "title": "결제 수단 확대",
      "open": false,                             // true면 [추가 논의 필요]
      "discussed": [Item],                       // 요약 표 '논의 내용'
      "agreed": [Item],                          // 요약 표 '조율 사항' (합의·범위 결정만)
      "points": [{ "label": "기술적 이슈", "items": [Item & { "children": [Item] }] }],
      "approach": Item | null                    // '접근 방식 정리' 한 단락 (있을 때만)
    }],
    "actions": [Item & { "team": "A팀" | null, "note": "비고" | null }],
    "next_meeting": [Line]                       // 다음에 볼 날. 말했을 때만 (0개 또는 1개)
  },
  "attendees": ["A팀", "B팀"],                   // 코어가 채움 (아래)
  "edited_at": null | "…",                       // 사용자가 칸을 고친 시각 (다시 만들기 전에 묻는다)
  "sections": [...]                              // 코어가 minutes에서 만든 v2 섹션 (내보내기 docx·MCP용)
}
```

`Item`은 기존 `summaries.Item`(text, segment_ids, owner, due)이다. `sections`를 함께 두는 이유는 기존 소비자(docx 내보내기, MCP `get_summary`, Obsidian)를 바꾸지 않기 위해서다. Markdown(`render_md`, 복사, md 내보내기)과 짧은 판은 언제나 `minutes`에서 그린다. 사용자가 고친 칸도 `minutes` 안에 있다.

**코어가 채우는 것 (AI에게 묻지 않는다)**

| 칸 | 출처 |
| --- | --- |
| 제목 `[YY.MM.DD] 노트 제목` | 노트 제목과 녹음 날짜 |
| 일시 `2026-10-20 14:00 · 4분` | 녹음 시각과 길이 |
| 참석 | 캘린더 일정 참석자 + 사용자가 확인한 참석자 이름에 붙은 팀(아래). 없으면 줄을 쓰지 않는다 |
| 요약 표 | `topics[].discussed`·`agreed` |
| 할 일 표 | `actions`를 팀별로 묶는다. 팀이 없는 할 일은 `담당 미정`으로 묶는다 |

## 프롬프트와 출력

**입력**: 기존 요약 입력(대화 내용 + 사용자가 적은 메모)에 두 블록을 더한다. 기존 요약 프롬프트는 바뀌지 않는다(새 함수).

```text
참석자 (사용자가 확인한 이름): 김지훈 (A팀), B팀
용어 표기 기준 (자주 쓰는 단어): Kubernetes, PostgreSQL, ...
```

용어 표기 기준은 그 노트의 자주 쓰는 단어(일정 참석자 → `--term` → glossary → 노트 낱말, 변환 때와 같은 목록)다. 범용 프롬프트처럼 분야 용어 보정 예시를 박아 두지 않는다. 다른 팀에서도 그대로 동작한다.

**규칙 (시스템 프롬프트, 기존 요약 규칙 위에 더함)**

- 대화에서 다룬 안건마다 topic 하나. 안건 순서는 대화 순서.
- `agreed`에는 합의·확정된 것과 범위 결정만 쓴다. 범위에서 빼거나 미룬 결정은 무엇을, 어느 범위에서, 왜 뺐는지를 대화에서 말한 그대로 쓴다.
- 정하지 못하고 넘어간 안건은 `open: true`. 지어내서 결론을 만들지 않는다.
- `points`의 이름표는 대화의 흐름을 드러내는 짧은 말(예: 기존 안, 기술적 이슈, 대안, 접근 방식)이고, 내용은 제안 → 한계 → 결정 순서로 쓴다. 이견이 있으면 양쪽을 모두 쓴다.
- **팀·사람을 주어로 쓰는 것은 두 경우뿐이다**: (a) 그 줄의 화자 표시가 사용자가 확인한 이름이고 거기 팀이 있을 때, (b) 말한 사람이 자기 팀을 직접 말했을 때("저희 B팀은 …"). 아니면 주어 없이 쓴다.
- 기한(due)은 말한 경우에만. 숫자·버전·수량은 대화에 나온 것만.
- 추임새·되풀이는 지우고, 문장은 개조식(`~함`, `~하기로 함`)으로 쓴다.
- 도식, 목적, 일시, `한계` 절은 만들지 않는다.

**검증 (어기면 1회 재요청, 기존 `complete_json` validate)**

- 모든 항목의 `segment_ids`가 입력 ID이고 비어 있지 않다(기존).
- topic이 하나 이상이다.

**후처리 (결정적, 재요청 없음)**: 지어내기 쉬운 값을 코어가 근거와 대조한다.

| 값 | 검사 | 어기면 |
| --- | --- | --- |
| owner | 기존 `clean_owners` (확인한 이름만) | null |
| action `team` | 근거 줄의 확인된 화자 이름 또는 근거 문장 안에 그 팀 이름이 있다 | null |
| due | 근거 문장에 날짜·요일·기간 표현(숫자, `월`·`일`·`주`·`요일`·`까지` 등)이 있다 | null |
| 문장 속 숫자 | 항목의 숫자(버전 `4.1`, 수량 `14일`)가 근거 문장에 있다 | 지우지 않고 `check: "number"` 표시 → 화면에 `숫자 확인` 배지 |

숫자는 음성 인식이 `사 점 일`처럼 글자로 적었을 수 있어 틀린 경고가 날 수 있다. 그래서 지우지 않고 표시만 한다.

## 팀 표기 (참석자 이름)

참석자 이름은 이미 사용자가 확인하는 값(`speakers.S1.name`)이다. 팀은 새 칸을 만들지 않고 이름에서 읽는다.

- `김지훈 (A팀)`처럼 괄호 안 → 이름 김지훈, 팀 A팀.
- 이름이 `B팀`처럼 `팀`으로 끝나면 → 그 자체가 팀(사람을 몰라도 팀으로 이름을 붙일 수 있다).

`store.speaker_name`은 그대로 이름 전체를 돌려준다(다른 화면은 바뀌지 않는다). 팀을 읽는 함수는 회의록만 쓴다. 자동 이름(`참석자 1`)과 제안 이름(`suggested`)은 쓰지 않는다(기존 규칙).

## 그리는 형식

두 사내 회의록의 부분을 합친 하나의 형식이다. 내용이 없는 부분은 그리지 않는다.

```markdown
# [26.10.20] 결제 기능 2.0 회의
참석: A팀, 김지훈 (B팀)                 ← 참석자가 없으면 없음
**주요 안건:** …                       ← agenda가 비면 없음

## 논의 사항 요약                       ← 안건이 2개 이상일 때만
| 구분 | 논의 내용 | 조율 사항 |
| --- | --- | --- |
| **결제 수단 확대** | • …<br>• … | • … |

## 회의 내용
### 1) 결제 수단 확대                   ← open이면 [추가 논의 필요]가 앞에
- **기술적 이슈**                       ← points (이름표는 AI가 고른다)
    - …
        - …                             ← children
**접근 방식 정리**: …                   ← approach가 있을 때만

## 향후 예정 작업                       ← 할 일이 있을 때만
| 할 일 | 담당 | 비고 |
| --- | --- | --- |
| … | A팀 · 김지훈 | 기한 금요일 · … |
```

표 칸 안의 여러 줄은 `• 항목<br>• 항목`이다. 사내 위키에 붙였을 때 어떻게 보이는지 보고 정한다(열린 질문).

## 시험

- **단위(가짜 LLM)**: 팀 읽기(괄호, `팀`으로 끝남, 자동·제안 이름 제외), 팀·기한·숫자 후처리, 그리기(내용이 없는 부분은 빠짐), 칸 저장(`minutes save`: 모양·근거 ID 검사, `edited_at`), 다시 만들기가 `edited_at`을 지우는지, 짧은 판, v2 `sections` 변환, 녹음 추가 시 근거 ID 옮기기.
- **회귀**: 다른 요약 유형의 프롬프트가 바이트 단위로 같다. 옛 `summary.json` 노트가 `이전 형식`으로 열린다.
- **실제 AI(`pytest -m llm -k minutes`, 가상 회의만)**: 새 가상 회의 fixture 1건. 팀을 말로 밝히는 사람과 밝히지 않는 사람, 범위 제외 1건, 차기로 미룬 결정 1건, 결론 없이 끝난 안건 1건, 숫자 3개, 기한을 말한 할 일 1건과 말하지 않은 할 일 1건을 넣는다. 본다:
  - 팀을 밝히지 않은 사람의 말에 팀이 붙지 않는가
  - 범위 제외·연기가 이유와 함께 `agreed`에 있는가
  - 결론 없는 안건이 `open`인가
  - 말하지 않은 기한·숫자가 없는가
- **사용자 노트(로컬, 사람이 판단)**: 사용자가 자기 회의 노트로 앱에서 만들어 실제 회의록과 비교한다. 회사 회의 내용은 저장소·테스트·벤치에 넣지 않는다.
- **화면**: `/preview.html` 라이트·다크, 폭 900·1280·1600.

## 하지 않는 것 (첫 구현)

- 예시 회의록을 붙여 넣어 형식을 따라 하게 하기: 예시의 내용(안건·팀 이름)이 새 회의록에 섞이는 환각이 알려져 있다.
- 형식 편집기(절 이름·순서): 두 형식으로 시작하고, 다른 팀 형식이 실제로 나오면 그때 정한다.
- 도식(텍스트 흐름도) 자동 생성.
- 메모 노트의 회의록.
- 위키로 바로 올리기(Confluence API): 복사로 충분한지 먼저 본다.

## 결정 (2026-10-20)

1. 회의록은 요약 유형이 아니라 녹음 노트의 별도 탭이다. 요약 탭에서 `회의록` 유형을 빼고, 옛 회의록은 회의록 탭에 `이전 형식`으로 보인다.
2. 앱 안에서 칸 단위로 고친다(줄, 할 일의 내용·담당·기한). 근거 ID가 남는다. Markdown 통째 편집은 하지 않는다 (2026-10-20, 처음의 Markdown 편집 결정을 바꿈).
3. 형식은 하나다. 두 사내 회의록의 부분(참석, 주요 안건, 요약 표, 번호 안건과 이름표 목록, 접근 방식 정리, 할 일 표)을 합치고, 내용이 없는 부분은 그리지 않는다. AI는 칸을 채우거나 비워서 부분을 고른다. 프롬프트가 각 칸이 회의록에서 어떻게 보이는지 알려 준다. AI가 Markdown을 직접 쓰지 않는 이유는 근거 ID가 사라져 담당·팀·기한·숫자 대조와 근거 칩을 쓸 수 없기 때문이다 (2026-10-20, 처음 결정한 두 형식 고르기를 바꿈).
4. 팀·사람을 주어로 쓰는 것은 대화에서 직접 말했거나 사용자가 참석자 이름에 팀을 붙였을 때뿐이다.
5. 실제 회의록에 없는 칸(일시 표, 목적, 기한, 도식, 한계 절)은 만들지 않는다.

6. 탭 순서는 `요약 · 회의록 · AI 질문 · 메모`다 (요약과 AI 질문 사이).
8. `짧게 복사`(메신저용 짧은 판)와 `다음에 볼 날`·일시(소요 시간)를 더한다. 담당·기한이 빈 할 일은 눈에 띄게 보인다.
7. 긴 회의도 한 번에 넣는다. `llm_context`(길이 초과) 오류가 나오면 그때 나눈다.
